## R1 — shadcn-vue Initialization in Nuxt 4 + Tailwind CSS v4

**Decision**: Use the official `shadcn-vue` CLI + `shadcn-nuxt` Nuxt module. Tailwind v4 uses CSS-first configuration — no `tailwind.config.js`.

**Rationale**: shadcn-vue is a CLI code generator that copies component source files into `components/ui/`. The `shadcn-nuxt` module registers that directory for Nuxt auto-imports, preventing console warnings. The CLI fully supports Nuxt 4 detection and Tailwind v4's `@theme inline` blocks.

**Alternatives considered**:

- **@nuxt/ui v3** — different API, opinionated design system, heavier footprint. Does not match the spec requirement for shadcn-vue.
- **Manual copy-paste** — tedious and error-prone for managing peer dependencies (`radix-vue`, `class-variance-authority`, etc.).
- **Tailwind v3 + tailwind.config.js** — spec and constitution require Tailwind CSS v4.

**Key commands** (in order):

```bash
# 1. Install Tailwind v4 as direct dependency
pnpm add -D tailwindcss @tailwindcss/vite

# 2. Install shadcn-nuxt module
pnpm dlx nuxi@latest module add shadcn-nuxt

# 3. Generate Nuxt types
pnpm dlx nuxi prepare

# 4. Initialize shadcn-vue (select: new-york style, CSS variables: yes)
pnpm dlx shadcn-vue@latest init

# 5. Add components
pnpm dlx shadcn-vue@latest add button
pnpm dlx shadcn-vue@latest add sheet
```

**Configuration artifacts**:

- `components.json` — generated by CLI; `tailwind.config: ""` (empty for v4), `style: "new-york"`, aliases use `@/`
- `lib/utils.ts` — `cn()` helper using `clsx` + `tailwind-merge`
- `nuxt.config.ts` — add `@tailwindcss/vite` to Vite plugins, add `shadcn-nuxt` to modules with `componentDir: './components/ui'`

**Theming strategy**: Site is always-dark (no light/dark toggle). All shadcn CSS variables defined directly in `:root`:

- `--primary` → Rust `#C9653D` (CTA buttons, active states, progress bar)
- `--secondary` → Teal `#2C7A83` (hover accents, secondary actions)
- `--background` → `#0e1516` (deep dark base)
- `--foreground` → `#e2dad0` (warm cream text)
- `--border` → `oklch(1 0 0 / 10%)` (subtle white borders)
- Custom `--color-rust` and `--color-teal` in `@theme inline` for direct utility classes (`text-rust`, `bg-teal`)

**Dependencies installed by shadcn-vue init**: `radix-vue`, `clsx`, `tailwind-merge`, `class-variance-authority`, `lucide-vue-next`

## R2 — Modern Lenis Package (Smooth Scroll)

**Decision**: Use the modern `lenis` package (v1.3.x), running on the GSAP ticker for a single unified RAF loop. Custom Nuxt client plugin — not the built-in `lenis/nuxt` module.

**Rationale**: Running Lenis on `gsap.ticker` guarantees a single animation loop for both Lenis and ScrollTrigger, avoiding dual RAF and 1-frame desync. The built-in `lenis/nuxt` module uses `autoRaf: true` (separate RAF), conflicting with our GSAP ticker requirement.

**Alternatives considered**:

- **`lenis/nuxt` module** — auto-registers `<VueLenis>` component, but uses its own RAF loop. No control over GSAP ticker sync, reduced-motion gating, or route-reset behavior.
- **`autoRaf: true`** — simpler, but creates a separate RAF from GSAP's ticker causing potential 1-frame scroll/animation desync.
- **`@studio-freight/lenis`** — deprecated predecessor. Must NOT be used (FR-014).

**Package**: `lenis` (currently `^1.3.17` in legacy package.json, existing dep to keep)

**Key patterns**:

| Concern        | Pattern                                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| Install        | `pnpm add lenis` (already a dep; remove `@studio-freight/lenis`)                                          |
| Import         | `import Lenis from 'lenis'`                                                                               |
| CSS            | `import 'lenis/dist/lenis.css'` (required for `.lenis-stopped`, scroll lock classes)                      |
| RAF            | `gsap.ticker.add((t) => lenis.raf(t * 1000))` + `gsap.ticker.lagSmoothing(0)`                             |
| ScrollTrigger  | `lenis.on('scroll', ScrollTrigger.update)` — no `scrollerProxy` needed                                    |
| Route reset    | `router.afterEach(() => lenis.scrollTo(0, { immediate: true }))`                                          |
| Reduced motion | Skip instantiation entirely, provide `null`                                                               |
| Cleanup        | `lenis.destroy()` + `gsap.ticker.remove(cb)` + unregister router guard; `import.meta.hot.dispose` for HMR |
| Access         | `provide: { lenis }` → `const { $lenis } = useNuxtApp()` with null-check                                  |

## R3 — Geist Sans Font Loading

**Decision**: Use `@nuxt/fonts` module with the `geist` npm package. The module auto-detects `font-family: 'Geist'` usage in CSS, self-hosts the woff2 files at build time, and injects fallback font metrics to eliminate layout shift.

**Rationale**: `@nuxt/fonts` is the official Nuxt font module. It generates `@font-face` with `font-display: swap`, SSR `<link rel="preload">` injection, and fontaine-based fallback metrics for zero CLS. Geist Sans is NOT on Google Fonts (Vercel proprietary), so CDN is not an option.

**Alternatives considered**:

- **Manual `@font-face`** — full control but no auto-preload, no fallback metrics, manual maintenance.
- **Google Fonts CDN** — Geist is not available on Google Fonts.
- **`@fontsource/geist-sans` directly** — requires manual `@font-face`; `@nuxt/fonts` already wraps fontsource.

**Key commands**:

```bash
pnpm add @nuxt/fonts geist
```

**Configuration**:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ["@nuxt/fonts"],
});
```

```css
/* main.css — Tailwind v4 theme */
@theme {
  --font-sans: "Geist", ui-sans-serif, system-ui, sans-serif;
}
```

The `--font-sans` override makes Geist the default for Tailwind's `font-sans` utility and preflight `body` rule.

## R4 — Nuxt 4 Page Transition Hooks

**Decision**: Use `useNuxtApp().hook('page:start', ...)` and `useNuxtApp().hook('page:finish', ...)` for the PageVeil. These are confirmed valid Nuxt 4 runtime hooks.

**Rationale**: Verified from Nuxt 4 source. `page:start` fires when Suspense enters pending state (old page still visible). `page:finish` fires after new component resolves + `nextTick` (new DOM ready). This is exactly the timing needed for a fade overlay.

**Alternatives considered**:

- **`<NuxtPage transition>` prop** — declarative but controls page content transition, not an independent full-screen overlay.
- **`page:loading:start` / `page:loading:end`** — earliest/latest but requires `pageKey` prop changes to fire reliably.
- **View Transitions API** — limited browser support, different UX model.

**Hook sequence during SPA navigation**:

```
1. page:loading:start    ← route watch triggers
2. page:start            ← Suspense onPending
3.   [new component resolves]
4. page:finish           ← Suspense onResolve + nextTick
5. page:loading:end      ← final cleanup
6. page:transition:finish ← Vue transition onAfterLeave
```

**Rapid navigation handling**: Store `setTimeout` ID, clear on each `page:start` to prevent stale timeouts from prematurely hiding the veil.

```ts
let veilTimer: ReturnType<typeof setTimeout> | undefined;

nuxtApp.hook("page:start", () => {
  clearTimeout(veilTimer);
  active.value = true;
});

nuxtApp.hook("page:finish", () => {
  veilTimer = setTimeout(() => (active.value = false), 300);
});
```

## R5 — `prefers-reduced-motion` with GSAP + Lenis

**Decision**: Two-layer approach — (1) `gsap.matchMedia()` for context-scoped GSAP animations with automatic revert on condition change, plus `gsap.defaults({ duration: 0.05 })` as a safety net; (2) conditional Lenis instantiation with `destroy()`/`create()` on mid-session toggle.

**Rationale**: GSAP has no automatic reduced-motion detection, but `gsap.matchMedia()` (GSAP 3.11+) auto-reverts/recreates animations when the media condition changes — ideal for ScrollTrigger-heavy components. Lenis has no built-in reduced-motion support, so we guard instantiation manually.

**Alternatives considered**:

- **CSS-only `@media (prefers-reduced-motion: reduce)`** — insufficient because GSAP sets transforms/opacity via JS. Added as a defense-in-depth CSS layer anyway.
- **`gsap.globalTimeline.timeScale(100)`** — opaque, affects delays, could cause sequencing issues.
- **`lenis.stop()` instead of `destroy()`** — Lenis still intercepts scroll events when stopped. `destroy()` fully removes all listeners.

**Composable**: Use `@vueuse/core`'s existing `useMediaQuery('(prefers-reduced-motion: reduce)')` — already a project dependency, returns reactive `Ref<boolean>`, handles SSR safely.

**Key patterns**:

| Layer               | Mechanism                                                                                                                                               | Scope                            |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| GSAP global default | `gsap.defaults({ duration: 0.05 })` in plugin if reduced-motion                                                                                         | Safety net for all animations    |
| GSAP per-component  | `gsap.matchMedia()` with two contexts                                                                                                                   | Auto-reverts on condition change |
| Lenis guard         | Conditional creation in plugin, `destroy()`/`new Lenis()` on `change` event                                                                             | Full lifecycle control           |
| CSS fallback        | `@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; } }` | Defense-in-depth                 |

**SSR note**: `window.matchMedia` not available during SSR. All detection must be in `.client.ts` plugins. VueUse composables return `false` / `'no-preference'` on server, so SSR always renders full-motion HTML. Client hydrates and adjusts.

## R6 — Testing Strategy (NEEDS CLARIFICATION resolved)

**Decision**: Manual verification against acceptance scenarios for Phase 1. Automated testing deferred.

**Rationale**: The spec defines clear acceptance scenarios (Given/When/Then) that can be manually verified in a browser. The constitution does not mandate a specific testing framework. Phase 1 is a visual/interactive foundation where manual testing is most efficient. Automated testing (Vitest for unit, Playwright for E2E) should be established in a future phase when there is logic to test beyond visual rendering.

**Alternatives considered**:

- **Vitest + Playwright from day one** — valuable but adds scope to a foundation-focused phase with no business logic to unit-test.
- **Storybook** — useful for component isolation but overkill for 4 layout components in Phase 1.
